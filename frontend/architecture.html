Production architecture for
agent-first systems

Simplify the data platform. Put agents to work. Keep decisions accountable.

Option A is a scalable production reference architecture built around open data formats, explicit business semantics, and controlled agent tools. The BASt application demonstrates a small implementation of the same pattern; production readiness requires workload-specific validation.

See the management briefing for the business case, adoption approach, and measures of success.

Production reference architecture

Seven responsibilities. Technology selected for the workload.

These responsibilities apply across domains and deployment sizes. The reference design defines what must be built and verified; the technology choices show one AWS implementation.

Responsibility Reference design
Data foundation Object storage with open table formats. Validated ingestion pipelines with schema enforcement. Retention and compaction policies and shared catalog for coordinated table access, publication controls, and data contracts across teams.
Query execution Embedded or distributed engines selected through workload benchmarks. Isolate tenants and workloads; set latency, memory, concurrency, and query-cost limits. Single-node execution can remain a production choice when it meets those requirements.
Business semantics Versioned entity definitions, relationship schemas, and metric registry. Tool contracts that describe what each agent tool does, its inputs and outputs, and what it can and cannot access. This makes data meaningful to agents.
Agent execution Bounded investigation loops with controlled tool access. Durable run state: investigations can be paused, retried, and resumed. Evaluation harness for regression testing. Resource budgets per investigation class. Cancellation support.
Actions Immutable proposals linked to server-retained evidence, with approval rules and verified reviewer identity. Record status transitions atomically. For operational execution, use durable dispatch, downstream deduplication, and reconciliation after uncertain outcomes. Keep approval state separate from execution state.
Security and operations Identity and enforced authorisation at every layer. Column- and row-level data access controls. Observability: structured logs, distributed traces, and cost metrics per investigation. Recovery procedures tested against failure scenarios. Deployment pipelines with rollback.
User experience Conversation interface alongside structured evidence, charts, and tables. Review queues for pending approvals. Action status tracking. The interaction model — question → investigation → evidence → approved action — is consistent whether the underlying stack is small or large.
The distinction that matters
Agents coordinate work. They select tools, run queries, test explanations, and assemble evidence. They do not enforce policy. Application and infrastructure controls enforce policy — data access permissions, approval rules, audit logging, and resource budgets. A well-designed system keeps these concerns separate. An agent that enforces its own policy is not a governed agent.
Technology implementation

Choices for each responsibility

Responsibilities drive technology selection: Not every use case inherits every component. Start with what the workload requires and expand when the evidence supports it.

Data foundation
S3 + Apache Iceberg v2
Iceberg adds table metadata, snapshots, and transactional commits over files on S3. Use a shared catalog for coordinated access and commits. Retain referenced metadata and data files for replay; validate engine compatibility with the table features in use.
Apache Iceberg v2 AWS S3 Nessie or Glue catalog
Query execution
DuckDB, Trino, or Athena
DuckDB for embedded and isolated analytical workloads; Trino for distributed execution; Athena for managed query execution. Select against latency, concurrency, memory, and cost targets. Shared Iceberg tables reduce data movement, but SQL and feature compatibility still need testing.
DuckDB (embedded) Trino (distributed) Athena (serverless)
Business semantics
Versioned entity module
Versioned code defines domain entities such as Asset, Shipment, or Station, their relationships, metric definitions, and tool contracts. Include units, coverage, limitations, and data provenance. Test semantics independently of the model.
Python module Tool contract registry
Agent execution
Claude via Bedrock Converse API
A tool-use loop invokes approved analytical capabilities. Persist investigation state, tool results, and evidence in PostgreSQL; add cancellation, retry budgets, and model/tool version records. Evaluate answer quality, evidence use, and tool selection. Stream progress to the user.
Claude + Bedrock FastAPI PostgreSQL (durable state)
Actions
PostgreSQL + event workers
RDS PostgreSQL stores immutable proposals, evidence references, and append-only transition history. A transactional outbox dispatches approved work to workers. Propagate idempotency keys to integrations that support them; reconcile timeouts before retrying uncertain external effects.
PostgreSQL Event-driven workers Idempotency keys
Security and operations
IAM + Lake Formation + CloudWatch
Use authenticated user identity and scoped service roles. With Glue and a supported query integration, configure Lake Formation filters and restrict direct S3 access that could bypass them. Other catalog/engine combinations require their own enforcement design. Instrument tool calls, approvals, costs, and failures in the application.
IAM + Lake Formation CloudWatch GitHub Actions CI/CD
Composability over completeness. A delivery investigation may work with hourly batches; a production-line response may require fresh events. Freshness, concurrency, isolation, and recovery targets determine the components. Industry or dataset size alone does not determine the stack.

Iceberg v2
Versioned tables with explicit publication. A catalog resolves a table to metadata; snapshots reference manifests and data files. Retain the selected snapshot, SQL, results, and metric version with investigation evidence. Ingestion emits the publication event explicitly; an Iceberg commit alone does not trigger an investigation.
Nessie
Optional versioned catalog. Nessie provides catalog branching and merge workflows when teams need them. Pipeline checks and review rules must validate schemas and data quality before promotion. A merge is not itself a data-quality guarantee; use Glue when that better fits the access and operations model.
Trino
Distributed query execution when required. Size coordinators and workers for the tested workload; define admission controls, memory limits, and capacity management. Benchmark representative queries and concurrency. Choose an execution environment that supports the required memory, temporary storage, and recovery behavior.
Governance
Enforcement follows the access path. Configure and test catalog, query-engine, and S3 permissions together. Application events capture investigation, evidence, and approval identities; configured AWS audit logs complement them. Exercise access-denial, restore, and failure scenarios before production release.

Production acceptance

Before launch, name the service owner and approve workload-specific latency, concurrency, availability, and recovery targets. Demonstrate access enforcement, query isolation, evidence retention, restore and rollback, and external-action retry behavior. Record benchmark results and runbooks against the deployed release.

Reference implementation

Demo: BASt traffic investigation

The repository implements the data, object, and proposal foundations of the production pattern. The table below reports source capabilities, not a claim that every path has passed live acceptance or production testing.

This is the reference implementation.
Published manifest: 15,176,273 station-hour observations across Jan–Jun 2025 and Jan–Jun 2026. Iceberg on S3, DuckDB, FastAPI on ECS Fargate, and Claude via Bedrock. Observation rows are distinct from summed vehicle counts; no independently measured cost or throughput benchmark is claimed here.
Architectural concerns Reference implementation: BASt Production extension
Data foundation Parquet data files committed to an Iceberg table on S3. A bundled manifest pins the metadata location and records the snapshot ID. Replaying older snapshots requires retaining their metadata and data files.
Implemented in source 		Shared catalog service (Nessie or Glue) with publication controls, access governance, retention policies, and data contracts. Validated ingestion pipelines with schema enforcement on arrival.
Query execution DuckDB inside FastAPI uses iceberg_scan() against the published metadata reference in ECS mode. Capacity depends on queries, memory, temporary storage, and concurrency; no fixed dataset-size ceiling is asserted.
Implemented in source 		Retain embedded execution where it meets requirements; isolate workers or select Trino/Athena when benchmarks justify it. Test engine compatibility, admission controls, and tenant isolation against the same data contracts.
Business semantics Station and Corridor objects through get_object(), with metric notes, coverage caveats, reporting period, direction, snapshot ID, and metric version. execute_sql remains available for additional analyses.
Implemented in source 		Versioned entity module with entity definitions, relationship schemas, metric registry, and tool contracts checked in and tested independently. Evaluation suite for regression testing semantic accuracy.
Agent execution Request-scoped tool-use loop via Bedrock Converse API with SSE progress. Object retrieval, SQL analysis, and proposal creation are wired in source. Durable investigation resume and production evaluations remain to be built.
Implemented in source 		Durable investigation state in PostgreSQL. Retry on transient failure. Cancellation support. Resource budget per investigation class. Evaluation harness with a test suite of known-answer questions.
Actions SQLite evidence and action stores; server-issued evidence IDs, payload-aware idempotency, and atomic pending → approved/rejected transitions with append-only history. Storage is ephemeral on ECS. Reviewer names are caller attribution, not verified identity. No operational write-back.
