Simplify the data platform. Put agents to work. Keep decisions accountable.

This page describes the production reference architecture for agent-first systems — responsibilities first, technology choices second. The BASt traffic investigation serves as a reference implementation that demonstrates the foundation and makes the path to production concrete.

See the management briefing for the business case and the five questions every deployment should answer.

Production reference architecture

Seven responsibilities. Technology choices follow from workload.

Each responsibility can be satisfied by more than one technology. The design choices below describe what each layer must do in production — the concrete options follow in the next section.

Responsibility Production design
Data foundation Object storage with open table formats. Validated ingestion pipelines with schema enforcement. Retention and compaction policies. A shared catalog for coordinated table access, publication controls, and data contracts across teams.
Query execution Embedded or distributed engines selected for the workload — single-node for small isolated queries, distributed for concurrent analytical load. Isolation between tenants or workloads. Latency targets set per query class.
Business semantics Versioned entity definitions, relationship schemas, and metric registry. Tool contracts that describe what each agent tool does, its inputs and outputs, and what it can and cannot access. These make data meaningful to agents — not just queryable.
Agent execution Bounded investigation loops with controlled tool access. Durable run state: investigations can be paused, retried, and resumed. Evaluation harness for regression testing. Resource budgets per investigation class. Cancellation support.
Actions Durable transactional storage for pending and completed actions. Idempotent execution: the same approved action can be safely replayed. Approval rules and role-based authorisation. Audit history with approver identity and evidence snapshot. Controlled integrations with operational systems.
Security and operations Identity and enforced authorisation at every layer. Column- and row-level data access controls. Observability: structured logs, distributed traces, and cost metrics per investigation. Recovery procedures tested against failure scenarios. Deployment pipelines with rollback.
User experience Conversation interface alongside structured evidence, charts, and tables. Review queues for pending approvals. Action status tracking. The interaction model — question → investigation → evidence → approved action — is consistent whether the underlying stack is small or large.
The distinction that matters
Agents coordinate work. They select tools, run queries, test explanations, and assemble evidence. They do not enforce policy. Application and infrastructure controls enforce policy — data access permissions, approval rules, audit logging, and resource budgets. A well-designed system keeps these concerns separate. An agent that enforces its own policy is not a governed agent.
Technology implementation

Concrete choices for each responsibility

Responsibilities drive technology selection — not the reverse. Not every use case inherits every component. Start with what the workload requires and expand when the evidence supports it.

Data foundation
S3 + Apache Iceberg v2
Object storage with ACID semantics, time travel, schema evolution, and partition evolution. The table format is portable — the same files work with DuckDB, Trino, Athena, and Spark.
Apache Iceberg v2 AWS S3 Nessie or Glue catalog
Query execution
DuckDB → Trino → Athena
DuckDB for single-node workloads and fast local development. Trino on ECS for concurrent analytical queries at production load. Athena for serverless pay-per-query. The upgrade path is the same Iceberg files — no data migration.
DuckDB (PoC / isolated) Trino (production) Athena (serverless)
Business semantics
Versioned entity module
A Python module — checked in, versioned, and tested — that defines the entities the agent works with (Station, Corridor, Period), the metrics available, and the tool contracts. Decoupled from the LLM; testable independently.
Python module Tool contract registry
Agent execution
Claude via Bedrock Converse API
Agentic tool-use loop with bounded tool access. Stream results back token-by-token. In production: durable run state via PostgreSQL, retry on transient failures, evaluation suite for regression testing of query accuracy.
Claude + Bedrock FastAPI PostgreSQL (durable state)
Actions
PostgreSQL + event workers
PostgreSQL as the durable action store — pending, approved, executed, and rejected states. Event-driven workers execute approved actions against operational integrations. Idempotency key per action prevents double-execution on retry.
PostgreSQL Event-driven workers Idempotency keys
Security and operations
IAM + Lake Formation + CloudWatch
IAM roles for service identity. Lake Formation for column- and row-level data access controls on the Iceberg catalog. CloudWatch for structured logs and investigation-level cost metrics. GitHub Actions for tested, repeatable deployments.
IAM + Lake Formation CloudWatch GitHub Actions CI/CD
Composability over completeness. A logistics use case investigating delivery delays does not need streaming ingestion or a multi-tenant query cluster. A manufacturing use case monitoring production lines across 50 plants does. Match the components to the workload and expand deliberately.

Iceberg v2
ACID transactions · schema evolution · time travel · partition evolution · compaction. The same Parquet files are queryable by DuckDB, Trino, Athena, and Spark without transformation. The PoC and production system share the same storage format.
Nessie
Git-like data branching: dev → staging → prod. Commit, merge, and rollback data changes like code. REST API. Self-hostable on ECS or as Dremio Arctic managed service. Schema validation on branch merge prevents bad data reaching production.
Trino
Distributed SQL at petabyte scale. Less than 10% performance gap versus Databricks on typical analytics queries. Runs on ECS Fargate — pay for what you use, scale horizontally. Separates storage (S3 + Iceberg) from compute cleanly.
Governance
Column- and row-level security via AWS Lake Formation. Amazon DataZone for business catalog and data discovery. Schema evolution without rewriting data. Audit trail via CloudTrail and CloudWatch for every query, every approval, every agent run.
Reference implementation

BASt traffic investigation — what it proves, what production adds

The demo is not a toy. It implements the same data contracts, tool contracts, and interaction model the production architecture requires. The gaps are explicit — not hidden.

This is the reference implementation.
1,943 counting stations · 12 months of vehicle records · 15 billion passages · Apache Iceberg v2 on S3 · Claude via Bedrock · FastAPI on ECS Fargate · ~€50/month. The purple chat button runs the agent live.

Architectures compared

Option A versus proprietary alternatives

The open-source production stack (Option A) delivers equivalent analytical capability at a fraction of the licensing cost. The performance gap is less than 10%. The licensing gap is 15×.

Option A is not about paying less. It is about paying for the right thing.
Databricks and Microsoft Fabric concentrate spend in platform licenses. The open-source path shifts that spend into delivery, domain knowledge, agent tooling, and embedded capability — clients pay for business outcomes, not infrastructure overhead.
