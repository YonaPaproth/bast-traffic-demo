Management briefing

Agent-first data
and operations

Simplify the data platform. Put agents to work. Keep decisions accountable.

Many operational questions require people to move between reports, source systems, spreadsheets, and specialist teams. An agent-first approach brings those steps into a connected workflow: agents gather evidence, test explanations, and prepare recommendations for people to review.

Open data foundations and reusable tools make it possible to start with a focused use case and expand into a governed production capability.

Applies to Infrastructure Manufacturing Logistics Finance Service operations
What changes?

From retrieving reports to preparing decisions

Move from retrieving reports to delegating bounded investigations and preparing decisions.

Today — fragmented handoffs
1
A question arrives. The person who has it opens three systems, pulls two reports, and waits for a specialist to confirm the numbers.
2
Data from different sources is reconciled manually in a spreadsheet. Context is lost in email threads. Assumptions are not recorded.
3
A draft answer arrives hours or days later. The decision window may have passed. The reasoning is not attached to the conclusion.
4
The next similar question starts from scratch. No institutional memory is built. The cost compounds across teams and months.
Target operating model — delegated investigation
1
A question is asked in natural language. The agent opens a bounded investigation: it retrieves evidence from connected, governed data sources.
2
The agent tests candidate explanations, runs supporting queries, and assembles the evidence with a concise rationale, assumptions, and unresolved questions.
3
A prepared recommendation is returned with evidence and limitations attached. The reviewer checks the case and decides. Response-time targets are set to match the decision window.
4
The investigation is retained: queries, results, data versions, decisions, and approver identity. Future investigations can consult this history while checking whether its evidence is still relevant.
The human role shifts, it does not disappear. Agents can reduce the mechanical work of pulling data, comparing sources, and drafting first versions. People focus on judgment, approval, and the decisions that carry accountability.
Where it applies

Recurring investigations across data sources

The pattern is the same across industries: a question, a bounded investigation, evidence, a prepared recommendation. The domain determines the data sources and the tool contracts.

Infrastructure
Investigate traffic changes, maintenance windows, corridor performance, and capacity constraints across sensor networks and counting stations.
Manufacturing
Diagnose production losses, unplanned downtime, quality deviations, and shift-level performance gaps across lines and plants.
Logistics
Investigate delivery delays, route deviations, carrier performance, and demand spikes against available capacity and contracted commitments.
Finance
Explain unusual transaction patterns, reconcile position changes, investigate activity against expected behaviour and regulatory thresholds.
Service operations
Triage service incidents, investigate SLA breaches, identify recurring failure patterns, and prepare escalation briefs from operational data.
The same data foundation, agent execution layer, and action controls apply in each case. Domain-specific work includes business semantics — entities, metrics, and tool contracts — together with data access, controls, and evaluation appropriate to the use case.
The case for simplification

Reduce duplicated data, overlapping tools, and integration work

Most organisations have accumulated data platforms, tools, and integrations faster than they have retired the old ones. The cost of that complexity is paid every quarter — in licensing, in maintenance, and in the coordination overhead agents must navigate.

01
Duplicated data
The same operational data copied across warehouses, lakes, and marts creates storage cost, consistency risk, and integration maintenance. Shared tables and coordinated catalog access can reduce unnecessary replication while retaining copies needed for recovery, performance, or regulatory separation. Agents use explicitly defined sources of record.
02
Overlapping tools
Overlapping query engines, BI platforms, and pipelines can add licensing, training, and maintenance costs. Retire redundant components only after their responsibilities are covered. Agents access stable tool contracts rather than navigating every underlying system.
03
Reinvest the savings
The capacity freed by simplification should move into domain knowledge — the entities, metric definitions, and tool contracts that make data meaningful to agents — and into adoption, controls, and outcome measurement. That is where the durable value is built.
Governance and accountability

Agents operate within boundaries. People approve what matters.

These are requirements for the target operating model. Production adoption must demonstrate that permissions, evidence retention, and approval boundaries are enforced by the application and infrastructure.

Permissions and budgets
The application enforces data permissions, query budgets, and tool scopes defined by the organisation. Verify these boundaries with access-denial and resource-limit tests; prompts alone do not enforce them.
Evidence with every recommendation
Recommendations reference retained evidence: the data version, queries, results, metric definitions, and a concise rationale. Reviewers can check assumptions and uncertainty against the source evidence.
Approval for consequential actions
Actions that affect external systems, trigger operational workflows, or carry organisational consequences require explicit human approval. The agent prepares and proposes. The authorised person approves and takes responsibility. That separation is structural, not optional.
Durable audit history
Persist investigations, approvals, and action events with timestamps, verified actor identities, and evidence references. Define retention and access rules, and test recovery. This history supports review, accountability, and improvement.
Measuring value

Define the baseline. Measure the shift.

Value claims without baselines are not defensible. Measure before starting; report against the same measures throughout. Present savings as something to measure, not a promised outcome — platform cost reduction depends on what is retired, not just what is added.

What to measure Baseline (before) Target direction Why it matters
Investigation time Measure elapsed time from question to reviewer-accepted answer Reduce median and slow-case times for the same question set Speed determines whether the insight is usable while the decision window is open
Answer quality Measure correctness, evidence support, and revision rate on a fixed question set Match or improve quality under the same review rubric Quality must match or exceed what was produced before — faster alone is not a win
Reviewer effort Measure reviewer time spent checking, correcting, and approving each answer Reduce review effort without lowering acceptance standards Track preparation effort separately so work is not merely shifted onto reviewers
Operating cost Total operating cost and cost per accepted investigation Compare the same scope, service levels, and cost categories Include infrastructure, licenses, inference, engineering, reviewer time, and operations; distinguish setup costs
Business outcomes The operational metric that prompted the original question Measured at 30, 90, and 180 days against the pre-implementation baseline The point is not the agent. The point is whether the operation improved.
See the approach in practice

Reference implementation: BASt traffic investigation

The reference implementation uses 15,176,273 station-hour observations from BASt across Jan–Jun 2025 and Jan–Jun 2026, as recorded in its published data manifest. It provides a concrete foundation for testing the approach; it does not establish production scale or business impact.

Implemented in the reference source
Natural-language SQL analysis and structured Station and Corridor tools, with metric definitions, coverage caveats, and data provenance
Iceberg snapshots on S3 with a published metadata reference; replay requires retained metadata and data files
Server-retained object evidence and action proposals linked by evidence ID, with duplicate-request handling and approval/rejection history in SQLite
The agent tools and API establish a path from questions to evidence and proposals. Verify endpoint behavior, tool selection, and approval transitions on the deployed revision
What it does not yet prove
Durable investigations with retry, cancellation, and evaluation at concurrent production load
Production approvals: durable storage, authenticated reviewers, scoped evidence access, and controlled external execution. Current SQLite storage is ephemeral and reviewer names are unverified attribution
Shared catalog with publication controls, data contracts, access governance, and retention policies
Load-tested availability targets and tested operational recovery procedures
Source implementation, deployed acceptance, and production readiness are separate milestones. Operational write-back and external explanatory data sources are not integrated. The architecture page describes the remaining requirements.
